- **Видение и дорожная карта.** [VISION.md](docs/plans/VISION.md) и [ROADMAP.md](docs/plans/ROADMAP.md) собраны из слов автора. Продукт создаёт коллекции, а не только карточки: стиль → коллекция → набор → карточка. Пайплайн агентский, человек почти не участвует: в редакторе он проверяет глазами и вносит небольшие правки на каждом этапе, а ручная генерация — крайний случай. Слово человека главнее любого правила, пока он не сказал иначе, агент строго следует библии стиля. Результат — несколько вариантов набора, включая золотые карточки; продукт работает локально, редактор — обычный сайт. Дорожная карта идёт по направлениям, а не по этапам. Промпты пишет агент или текстовая модель, не человек. На будущее: замена отдельных элементов стиля, LoRA стиля для локальной бесплатной модели, портал сервисов с MCP. Позже добавлены: модель по умолчанию Nano Banana 2.1, запасная — GPT Image, свои пробы идут через Codex CLI; проверка результата включает адекватность (нет того, чего не заказывали, например лиц у рыб); готовое лежит в `collections/` вне Git; обработка после генерации обязательна; постановку, которой нет в эталоне, агент выбирает только по прямой просьбе человека.

- **Стиль Scapes: библия и эталоны.** `styles/scapes/` — первый стиль. В Git лежат все 160 эталонных карточек (46,9 МБ, ниже порога автора в 50 МБ) и указатель с постановкой каждой. Библия принята автором: `BASE_RULES.md`, `COLOUR.md`, `BACKGROUNDS.md`, `RENDERING.md`, `COMPOSITION.md`, `CHARACTERS.md`, `SETS.md`, `CHECKLIST.md`, `PROMPTS.md`; у каждого факта есть источник. Ответы автора на открытые вопросы: основной свет сверху слева, сооружение на ровном небе — категория 4, стена ровного цвета — 2, не больше половины общих видов у вариантов набора, неповторение действует на всё заметное, сооружение-герой в фоне чужого набора допустимо только если объяснено темой. Резкость решена: лёгкая резкость входит в обработку. Шаблоны окна набора — четыре, цвет переключает пользователь. Автор выбрал Nano Banana 2.1 из трёх моделей по пяти пробным карточкам.

- **Стек и установка.** Автор поручил агенту выбрать стек и одобрил выбор (VISION.md, «Устройство и стек»): одно ядро операций для команд агента и сервера редактора, только Node без фреймворка, JavaScript с типами в комментариях и проверкой TypeScript, без сборки, данные — файлы, картинки — `sharp`. Запуск одной кнопкой: `run.command`, `run.sh`, `run.bat` вызывают `tools/setup.mjs`, который сверяет версию Node, ставит пакеты и проверяет `sharp`. Проверки Scapes перевели с ffmpeg на `sharp` (блок iCCP вырезается, чтобы мерить записанные значения): контрольный прогон по 160 эталонам до и после дал побайтно одинаковый результат.

- **Провайдеры и модели.** `core/providers/openrouter.js` (генерация с образцами стиля, список моделей, остаток, ключ из окружения или `.env`, повтор при 429 и 5xx) и `codex-cli.js` (проверено на живых запусках: картинка 4:5, без платы, размер задаётся только словами). Значения провайдеров лежат в `settings/defaults.json`, личные — в `settings/local.json` (не в Git); тесты берут настройки из временной копии (`CCF_SETTINGS_DIR`). Запасная модель при сбое основной — `openai/gpt-image-2.5-flare`: единственная из трёх GPT Image, что прошла пробы автора. Число попыток (3) и потолок ($0,20 за запуск) выбрал помощник, автор их не решал. `--provider` в `card make` меняет провайдера одного запуска.

- **Подготовка и обработка картинки.** `core/image/prepare.js` приводит картинку модели к пикселям карточки по `BASE_RULES.md` (масштаб до покрытия, обрезка по центру, Lanczos-3), прозрачную отвергает. Начальные настройки обработки зависят от модели, а `core/card/tune.js` подбирает их под каждую карточку: сначала насыщенность и яркость по мерам цвета, затем резкость, при наименьшем сдвиге, в границах из `styles/scapes/processing.json`. Причина: одинаковые настройки выводили уже насыщенные картинки за норму. Ручные значения человека больше не подбираются.

- **Запрос к модели и проверки Scapes.** Запрос собирает `core/style` из фрагментов библии (невидимые метки `<!-- fragment: id -->` в документах, правила сборки — `styles/scapes/prompt-assembly.json`, по две эталонные карточки на запрос). Недостающие фрагменты дописаны только по тому, что библия уже описывает, и помечены как не проверенные генерацией. Проверки как код — `styles/scapes/checks/` (`check-card.mjs`, числа только в `thresholds.json`, постановка 160 эталонов в `reference-spec.json`, пробы обработки `adjust-trial.mjs`): все эталоны проходят, кроме названных в библии исключений.

- **Цикл карточки.** `core/card/make.js`: заказ → запрос → генерация → обрезка и обработка → проверки; пока есть блокирующий FAIL, программа генерирует заново в пределах попыток и потолка расходов (проверяется перед каждым платным вызовом по самой высокой известной цене); лучшая попытка становится `card.png`. Решения автора: готовые данные в `collections/` вне Git, программа сама перегенерирует до просмотра агентом. Операции для агента и человека: перегенерация с пожеланием (слова человека дописаны в запрос как есть), правка картинки, ручная обработка, импорт картинки агента; просьба человека — одна попытка. FAIL на неподтверждённом контуре героя перегенерацию не запускает.

- **Контур героя и взгляд смотрящей модели.** Раньше контур давала заливка от краёв и была верна на 1 из 8 предметных карточек, поэтому цветовые проверки «герой против фона» почти не мерились. Теперь контур вырезает GrabCut (`core/image/segment.js`, чистый JS) в рамке героя от агента, человека или смотрящей модели (`google/gemini-3.5-flash-lite`, выбор автора; рамке верят, только если два взгляда — на карточку и на зеркало — совпали). Измерено на 160 эталонах и 13 попытках: рамка на глаз даёт верный контур в 172 случаях из 173 против 77 у старого способа. Нормы, зависящие от контура, перемерены на 81 эталоне: для героя на полу, опоре или стене нарушения — WARN, а не FAIL, верхняя полоса считается с 38 px. Известный сбой: светящаяся плашка за героем уходит в контур. В редакторе замечания смотрящей модели видны в панели карточки, её можно выключить в настройках («Взгляд на карточки»).

- **Опорные портреты персонажей.** Вид заказа `character-sheet` (портрет в полный рост на светло-сером фоне, кадр 2:3, без обрезки и пиксельных проверок). По решению автора опорными стали портреты Codex без обработки, свинья без одежды: `styles/scapes/characters/{man,pig,sheep,rooster,cow}.png`, разбор «канон или придумано» — в `characters/README.md`. Сцены прикладывают их как образцы.

- **Хранилище, наборы и коллекции.** `core/store/`: коллекции, наборы и карточки лежат файлами в `collections/`; карточка живёт в коллекции один раз, набор ссылается на неё из слота (в одном слоте не больше одной карточки, перенос в занятый слот меняет местами); id читаемые, удаление — в корзину ОС. `core/set/`: план набора (10 слотов) проверяется по `SETS.md`, раздел 9, коллекция — 16 наборов, гранд последним; человек может отступить от правил, тогда ошибки становятся предупреждениями. Без агента план пишет текстовая модель, ошибки уходят ей на исправление; карточки набора делаются по несколько сразу под общим потолком расходов.

- **Редактор и команды.** `editor/` — локальный сервер на `node:http` без фреймворка (только 127.0.0.1, токен запуска, ключ виден 4 последними знаками), API — по операции ядра на адрес, долгие операции — задачи с остановкой и живыми событиями. Экраны: коллекции, коллекция, набор, панель карточки; предпросмотр обработки считает общий с ядром `core/image/adjust.js`. Дизайн-система `editor/design-system/` принята автором: переделка «Монолита» под редактор, значения только в `DESIGN.md`, две темы. `ccf.mjs editor` запускает редактор в фоне и открывает коллекцию человеку; платные команды без ключа выполняются в запущенном редакторе. `ccf.mjs` даёт команды карточек, наборов, коллекций, выгрузки.

- **Скиллы проекта.** По решению автора о разбиении (VISION.md, «Проект на скиллах»): для работы с фабрикой — `ccf-make-cards`, `ccf-make-sets`, `ccf-review-cards`; для разработки — `ccf-core`, `ccf-style`, `ccf-editor`. Таблица скиллов — в `AGENTS.md`, правила — в [agents/README.md](agents/README.md).
